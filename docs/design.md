# 设计与维护说明

[返回首页](../README.md)

## 范围

**做的事**

- 接收链接：可以是单纯的链接，也可以是 B 站 App 分享出来的整段文字。
- 只接受 B 站（bilibili.com、b23.tv）和 YouTube（youtube.com、youtu.be）。
- 检查是否重复、是否超过额度，然后立刻回复一句结果。
- 排队，一次下载一个，存到 `D:\Share\2026-11-22\标题 [视频ID].mp4`。
- 把封面和人工字幕（中文、英文）嵌进 mp4 文件里。
- 下载完成或失败时，发 Telegram 通知。
- 提供一个只能在本机打开的管理页面：显示额度、列表，也可以在这里提交链接。

**故意不做的事**

- 不能从外部修改额度：接口里没有这个功能，页面上也没有。想改额度只能去改 `config.toml` 并重启服务。
- 不转码：所以几乎不占 CPU。
- 不下载直播、合集和播放列表。
- 不下载弹幕，也不下载 YouTube 自动生成的字幕。
- 暂时不做归档同步，也不做推荐。

## 架构

### 整体流程

```
 ┌──────────── iPhone / Mac ────────────┐
 │  B 站 / YouTube App → 分享 → Telegram  │
 └──────────────────┬───────────────────┘
                    │ 消息（Telegram 服务器保存 24 小时，电脑离线也不丢）
                    ▼
 ┌──────────────────────── 宿舍 Windows 电脑 ─────────────────────────┐
 │                                                                     │
 │   dsh（agent）                                                       │
 │     │ 从消息里提取链接                                                 │
 │     │ POST http://127.0.0.1:8765/api/links   (X-API-Key)             │
 │     ▼                                                               │
 │   ┌──────────────────── MediaBox（Windows 服务）──────────────────┐ │
 │   │                                                               │ │
 │   │  接口层 app.py (FastAPI)  ── 只监听 127.0.0.1                    │ │
 │   │     │                                                         │ │
 │   │     ▼                                                         │ │
 │   │  业务层 service.py                                             │ │
 │   │     ├─ 提取链接 / 检查平台      downloader.py                     │ │
 │   │     ├─ 解析视频信息（不下载）   downloader.py → yt-dlp            │ │
 │   │     ├─ 查重 + 查额度           quota.py + db.py                  │ │
 │   │     └─ 写入队列（queued）      db.py → SQLite                    │ │
 │   │                                                               │ │
 │   │  下载线程 worker.py  ← 一次一个，按提交顺序                        │ │
 │   │     ├─ yt-dlp + ffmpeg 下载、合并、嵌入封面/字幕                   │ │
 │   │     ├─ 更新状态 done / failed                                   │ │
 │   │     └─ notify.py → Telegram Bot API（只发不收）                   │ │
 │   └───────────────────────────────────────────────────────────────┘ │
 │                    │                                                │
 │                    ▼                                                │
 │     D:\Share\2026-11-22\标题 [BV1xxxx].mp4   ← SMB 共享              │
 └────────────────────┬────────────────────────────────────────────────┘
                      │ Tailscale + SMB
                      ▼
            iPhone / Mac 上的 VLC 观看
```

### 组件

| 组件 | 文件 | 用到的技术 | 职责 |
|---|---|---|---|
| 启动入口 | `run.py` | uvicorn | 读配置、设置日志、把 ffmpeg/deno 加进 PATH、启动服务 |
| 配置 | `mediabox/config.py` | tomllib（Python 自带） | 读 `config.toml`，相对路径按项目文件夹解析，配置错了就拒绝启动 |
| 接口层 | `mediabox/app.py` | FastAPI | 校验密钥，把请求交给业务层，返回 JSON |
| 业务层 | `mediabox/service.py` | — | 提交链接的完整流程、查询状态 |
| 额度规则 | `mediabox/quota.py` | — | 「一天」怎么算、能不能放行。整个软件的规矩都在这一个文件里 |
| 下载 | `mediabox/downloader.py` | yt-dlp（作为库调用）+ ffmpeg | 提取链接、检查平台、展开短链接、解析信息、下载 |
| 存储 / 队列 | `mediabox/db.py` | SQLite（Python 自带） | 一张 `items` 表同时充当下载记录和队列 |
| 下载线程 | `mediabox/worker.py` | threading | 从队列里取任务、下载、更新状态、发通知 |
| 通知 | `mediabox/notify.py` | urllib（Python 自带） | 调用 Telegram 的 `sendMessage` |
| 管理页面 | `mediabox/static/index.html` | 原生 HTML + JS | 显示额度和列表，提交链接 |
| Windows 服务 | `scripts/install-service.ps1` | NSSM | 开机自动启动，崩溃后自动重启 |
| 自动更新 | `scripts/register-update-task.ps1` | 任务计划程序 | 每周更新一次 yt-dlp |

除了 FastAPI、uvicorn 和 yt-dlp，其他用的都是 Python 自带的模块。

### 一条链接的完整经过

**第一阶段：提交（接口层，几秒内回复）**

1. **记下收到请求的时间**，按凌晨 2 点的分界算出它属于哪一天。之后解析花了几秒钟，也不会影响算哪一天。
2. **提取链接并检查平台**。这一步不联网，不是 B 站或 YouTube 的链接直接拒绝。
3. **粗查额度**：今天已经用完的话直接拒绝，省得再联网去解析。
4. **解析视频信息**：调用 yt-dlp，只取信息、不下载，拿到视频 ID、标题、时长，以及是不是直播、是不是合集。b23.tv 短链接会先展开，并检查展开后是不是 B 站。
5. **加锁后完成三件事**：按视频 ID 查重、精确查额度、写入队列。两个请求同时到达时，也不会都钻过最后一个名额。
6. **唤醒下载线程**，然后回复，比如「已加入：《xxx》（12分钟）。今天已用 57/90 分钟，3/5 个。」

**第二阶段：下载（后台线程）**

7. 取出最早的一条「排队中」的记录，标记为「下载中」。
8. yt-dlp 下载视频，最高 1080P。音频和视频由 ffmpeg 合并成 mp4，同时嵌入封面和字幕。合并只是重新封装，不转码。
9. 成功后把状态改为「完成」，并发通知。如果是 B 站视频，而且画质低于 720P，会额外提醒你 cookie 可能过期了。
10. 失败后把状态改为「失败」，并发通知附上原因。失败的记录不计入额度。
11. 如果嵌入字幕或封面出错，会去掉这两项再下一次，不会因为字幕问题让整个视频下载失败。

### 状态

```
queued（排队中） → downloading（下载中） → done（完成）
                                       ↘ failed（失败，不计入额度，可以重新提交）
```

如果程序崩溃或电脑关机时有视频正在下载，下次启动会把它重新标记为 `queued`，从头再下。

### 为什么这样设计

| 决定 | 原因 |
|---|---|
| 额度写在代码里，不交给 dsh | 大模型会犯错，也能被说服。额度是给自己定的规矩，必须由固定的代码执行 |
| 只监听 127.0.0.1 | dsh 和管理页面都在这台电脑上，不需要对 Tailscale 网络开放，外面访问不到 |
| 提交时就判断额度，而不是下载时 | 被拒的话当场就知道，不会排队几分钟后才发现下不了 |
| 日期按提交时间算 | 晚上发的链接即使排队到第二天凌晨才下完，也算在发链接的那天 |
| 用视频 ID 去重，而不是链接 | B 站每次分享出来的短链接都可能不一样，视频 ID 不会变 |
| 失败的记录不计入额度 | 用统计时排除失败记录的方式实现，不需要另写「退还额度」的逻辑 |
| 一次只下一个 | 降低被 B 站限速、风控的概率，也更容易排查问题 |
| 用 SQLite 当队列 | 不用另外装 Redis 之类的东西。重启后队列还在 |
| 不转码 | 转码是唯一会吃 CPU 的环节，一个视频就能让 CPU 满载好几分钟。这里完全避开了 |
| Telegram 通知由 MediaBox 直接发 | 结果是确定的，不依赖 agent 记得去查。只发不收，所以和 dsh 共用一个 bot 也不冲突 |

## 额度与内容规则

| 规则 | 具体内容 |
|---|---|
| 每日额度 | 提交时已用时长不足 **90 分钟**、已用名额不足 **5 个**，才能再收一个视频 |
| 一天的分界 | **凌晨 2 点**。凌晨 1:59 提交的仍然算前一天，文件也放进前一天的文件夹 |
| 透支 | 只要提交时「已用时长 < 90 分钟」而且「已用个数 < 5 个」，就放行，哪怕这个视频比剩余时长还长。超出的部分不会从第二天扣，但当天就不能再下了 |
| 超长视频 | 比 90 分钟还长的视频（比如一节 2 小时的课），只要提交时两项额度都有剩余，也能下载 |
| 重复 | 同一个视频只要处于「排队中」「下载中」或「已完成」，就算重复：不下载，也不扣额度 |
| 失败 | 不计入额度，可以重新提交 |
| 分 P 视频 | 只下载你发的那一 P，不会把整个合集都拉下来 |
| 直播 | 不支持 |
| 学习视频 | 不单独处理，和其他视频一样计入额度 |
| 计算方式 | 判断额度使用秒数。显示时，已用时长**向上取整**到分钟（不会少算），剩余时长**向下取整**（不会多算） |

## 后续想法（未列入计划）

- **归档同步**：把视频拖进 `D:\Share\保留\` 文件夹，就当作标记了。再用 rclone 定时上传到 WebDAV 网盘，超过 N 天的日期文件夹自动删除。
- **在 Mac 上打开管理页面**：在宿舍电脑上运行 `tailscale serve --bg 8765`，Tailscale 网络里的设备就能通过 HTTPS 打开页面了。MediaBox 本身不用改。
- **推荐**：数据库里已经记录了下载过的每一个视频，以后做推荐可以直接用这些数据。
